The model

The project's decisions can accompany the next task as reviewable work.

ArqUX organizes rules, context and evidence outside an isolated conversation, so you can recover what was agreed, who was meant to act and what was verified — within the mechanisms your environment provides.

From agreement to result

A shared decision can become a verifiable task.

First the work's rules are agreed. Then a responsibility is assigned, permitted actions run under the applicable controls and the result is reviewed. Not every step requires automation: some remain under the team's decision.

For example: the team agrees that errors must not show sensitive data. The criterion joins the work through the corresponding artifacts and controls, and the review checks the result.

Learning with criteria

The project can learn without turning every finding into a rule.

A task can leave a lesson behind. ArqUX distinguishes that record from the criterion incorporated into future work: promotion follows the review route or the configured policy.

Finding recorded→Evaluation or policy→Criterion available
  • 01Keep what was observedA lesson stays available as a finding; it does not yet govern other tasks.
  • 02Decide whether it should be incorporatedDepending on the route, a proposal is reviewed with a hash or a configured policy is applied.
  • 03Consult the approved or incorporated criterionAnother task can use it if its context and mechanisms make it available; the result stays subject to review.

In the home example, the error-message decision could be recorded as a finding; incorporating it into the active criterion is a separate step.

See the promotion routes and their controls

From work to reusable criterion

  1. 01WorkThe agent implements; the team agrees not to expose sensitive data in error messages.

    decision · work

  2. 02IdentifyThe decision is recorded as a lesson or proposal — a finding, not yet an active criterion.

    criterion · record

  3. 03Review and incorporateThe applicable route decides: the inspected path (identity.elevate) proposes in dry-run and applies only with the proposal's hash confirmed (confirm_hash); other routes can run under a configured policy. If accepted, the available mechanism incorporates it into context.

    review · dry_run · confirm_hash · policy

  4. 04Reuse and reviewAnother task may consult the available criterion, and the result is reviewed.

    context · review

A recorded lesson is not yet an active criterion; incorporation depends on the route and on the mechanism available in the installed version. The verified first task shows the CLI path: See the first governed task →

Environment freedom

You can add governance without adopting a single agent.

ArqUX places governance in the project. The environment adheres through instructions it can read and, when the client supports and is configured for them, through MCP operations. Concrete capabilities depend on each client.

How an environment adheres

Project instructions — sync-harnesses generates files for four implemented conventions and drift-check detects differences when you run it.

MCP operations — arqux serve exposes the governance handlers over stdio; the configuration is external and belongs to each client (the pinned guide shows Cursor as an example). A client without MCP support can still adhere through files.
