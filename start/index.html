What "from source" means here

pip install -e . installs the revision you checked out, in editable mode, inside the virtual environment: it reproduces exactly the inspected 1.0.0 source for this test. It is not a PyPI release and it does not update itself when the repository moves on.

Requirements: Python 3.10 or newer (verified on 3.11.12), Git, a POSIX shell and a directory you can write to.

Important: at the 2026-11-20 verification, PyPI served 0.9.0 — pip install arqux did not reproduce this guide. Version 1.0.0 is installed here from the pinned revision; check the PyPI JSON API ↗ before assuming it is already published.

Why a pinned commit

The commit 390333913e0f071a89241187f36cc90289e7e043 corresponds to version 1.0.0 in the public repository's pyproject.toml. Checking it out reproduces the inspected source; it is not a package publication and does not guarantee the repository HEAD is identical.

python3 -m venv .venv creates a virtual environment inside the cloned folder and source .venv/bin/activate activates it in POSIX shells; on other shells use their own activator. Keep the environment active — or prefix commands with .venv/bin/ — when running the first task.

If PyPI publishes 1.0.0 and it is verified, this section will show that command as the primary channel.

Create my first task

First checkable result

Create a file, complete a task and review its evidence.

This ArqUX 1.0.0 sequence creates first-task.txt containing hello-from-arqux, marks T-001 as done and records evidence. You can inspect each result from the same workspace.

Verified by execution · Linux · Python 3.11.12 · commit 3903339 · CLI without an agent · 2026-11-20

The result

  • File createdfirst-task.txt contains hello-from-arqux.
  • Task closedT-001 ends done; PULSE event SES001-E0002.
  • Inspectable trailA SHA-256 hash is recorded as evidence and the timelog keeps a record under .arqux/.

How to run it

  • PrepareCreate the arqux-first folder, activate the environment from the previous step and set ARQUX_EXECUTION_KEY for the whole session.
  • Declarearqux init, project Demo, cycle CYCLE-01, session context and the task to create.
  • Run and closeRun T-001 and complete it with the file hash as evidence.
  • InspectRead first-task.txt and compare the result with the recorded evidence.

Scope of this check: the sequence ran through the CLI — no agent took part, and it does not prove model reasoning or how a specific harness behaves. The timelog reports a real pending notice — operation 'task:T-001' is not recorded in this timelog — about an operation missing from that block; it does not change that T-001 closed.

View and copy the full sequence

The full sequence

mkdir arqux-first && cd arqux-first
export ARQUX_EXECUTION_KEY=first-task-demo
arqux init
arqux project init name=Demo
arqux cycle create name=CYCLE-01 description="First governed task"
arqux call session.context_set project=Demo scope=CYCLE-01
arqux call task.create content='$1:{obj:"Create a first governed artifact",proc:["Write first-task.txt [exec:write_file path=first-task.txt content=hello-from-arqux]"],ac:["first-task.txt contains hello-from-arqux"],complexity:"simple"}'
arqux call task.run task_id=T-001
arqux call task.complete task_id=T-001 evidence="first-task.txt sha256=$(sha256sum first-task.txt | cut -d' ' -f1)"
cat first-task.txt
Requires a POSIX shell (export, sha256sum, $(...)), ArqUX 1.0.0 installed and a writable directory. Run the commands exactly as shown, in order; the execution key must be the same across all of them.

Connect your environment

Choose how your agent receives the project's governance.

ArqUX offers two complementary ways to adhere: instruction files your client can read and MCP operations if the client supports that connection. Start with the route that fits your tool.

Route A · My agent reads instruction files

Run arqux init once, then arqux sync-harnesses projects the instruction kernel into the files each environment reads natively.

cd /path/to/workspace
arqux init
arqux sync-harnesses
  • What you doRun arqux init and arqux sync-harnesses inside the project root.
  • What you getFiles such as AGENTS.md, CLAUDE.md, GEMINI.md and .opencode/instructions.md, following the applicable convention.
  • What you checkVerify your client actually reads the right file; run arqux drift-check if you want to detect differences from the source.
Each harness reads its own native file (AGENTS.md is the generic one). ArqUX does not run the sync for you, and the files' presence alone does not guarantee the agent obeys them — instructions orient the model; they are not a code-enforced restriction.

Route B · My client supports MCP operations

arqux serve exposes the governance handlers over stdio to MCP-capable clients. Configuration is external: each client defines its own.

cd /path/to/workspace
arqux serve
  • What you doStart arqux serve in the project and configure the connection in your client.
  • What you getAccess to the operations the server exposes, within the permissions and limits the code implements.
  • What you checkRun a read operation such as workspace.status before trusting it with other actions.
One workspace per process. ArqUX does not configure clients automatically; if your harness offers no MCP, route A file adhesion still applies.
Claude Desktop config — one specific example
Adapt cwd to your workspace:
{
  "mcpServers": {
    "arqux": {
      "command": "arqux",
      "args": ["serve"],
      "cwd": "/path/to/workspace"

Compatibility by environment

The compatibility matrix is the canonical reference: four implemented file-projection conventions, MCP where the client allows it, and the verification status of each environment. Appearing there does not imply automatic MCP setup or an identical integration level; harness behavior and client configuration stay outside ArqUX.
