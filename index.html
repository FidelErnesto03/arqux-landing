The coordination problem

Work should not restart with every session.

Instructions, decisions and context scatter across chats, repositories, tools and people. A new agent or workstation can begin from a different local view of the same project.

Without a shared standard
Objective of the governed model
Rules spread across conversations and files.
Working rules have a governed source and a visible local projection.
Agents receive different instructions.
The team can inspect the intended version for each workspace.
Tasks lack shared scope and closure criteria.
Work is organized into explicit, reviewable units.
State depends on one session's history.
Persistent artifacts help the next session continue.
Review sees mostly the final answer.
Changes and available evidence can be inspected.

Actual enforcement, propagation and conflict handling depend on the Framework version and the workspace mechanism. This concept does not imply automatic synchronization.

The local-file model

One governed project. Instructions where agents can read them.

Today, arqux init creates a governed project directory with local instructions and artifacts. Agents that can access the same project can read its governance files. A service that propagates and reconciles policy across independent workspaces is a product direction, not a capability of v0.9.0rc3.

Codec‑CORTEX

Every line is one idea.

CORTEX keeps an agent's memory ultra-dense: each line carries one idea — a sigil, a name and a payload — so the model spends tokens on signal, not on filler. The same document renders for humans (HCORTEX) and canonicalizes for machines, deterministically.

CORTEX · machine sourcerepository sample · envelope 1.0
$0:KERNEL
$0:format{cortex:1.0,encoding:UTF-8,language:en}
OBJ:task{type:attrs,weight:H,
 fields:"goal:text|status:%state",
 focus:goal,schema:table,desc:"Task"}
$1:CORE
OBJ:meta{goal:"Learn HCORTEX",status:current}
OBJ:gate{goal:"Write documentation",status:planned}

Signal, not filler

The unit is the idea

Norms live in typed ideas (RUL · API · PRC · TST), not in prose. The project's own rule: efficiency is tokens of signal, not of filler.

Microtokens

Syntax compression

Any atom repeated three times or more becomes a one-token alias, expanded only in canonical form — the source weighs less, the hash does not change. The one compressor Markdown cannot offer.

Canonical and reversible

Same bytes everywhere

The same entry produces the same canonical bytes across runtimes; HCORTEX is a canonical rendering, not a second source. Certified: 141/141 · 101/101 · 5/5.

Why not just YAML/JSON/Markdown? ›
They can hold data, but they have no idea-level unit, no local-glossary layer and no canonical expansion — density and reversibility become accidents of how you write them, not properties of the format. CORTEX makes them contract. Limits still apply: density is a representation property (bytes · tokens · repetition), not a comprehension claim; token advantages publish with a neutral corpus and declared limits, per the project charter. Evidence, with scope

Separate what is proven from what is being checked.

A test of Codec‑CORTEX does not certify Framework behavior or agent security. Each claim belongs to a component and a version.

Available evidence · Codec‑CORTEX

Reversible format, measured within scope.

The published certificate (codec_cortex 1.0.0) reports 141/141 for idempotence, round-trip and lossless checks, 101/101 HCORTEX render-parity cases, and 5/5 runtime parity. These results do not certify ArqUX Framework behavior or prove that an LLM understands the format better.

Trust and limits

Know what is enforced—and what depends on the agent.

A written rule, a permission check and a human practice are different controls. ArqUX should make that difference visible.

01

Applied by code

Handler permissions, validation and state changes only where the release implements and tests them.

02

Read by the harness

Local instruction and context files shape an agent's work; they do not automatically guarantee obedience.

03

Owned by the team

Approval, review, synchronization and key handling depend on the documented workflow and its actual controls.

A hash can detect a mismatch against a trusted reference. It is not by itself a signature or an independent audit.
