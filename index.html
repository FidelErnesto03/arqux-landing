The problem

Work shouldn't restart with every session.

Decisions, rules and knowledge scatter across conversations, repositories, files and people. Every agent or session can receive a different context. The team re-explains the work — and later can't tell what was decided, what changed, and what should be reviewed.

Without a common structureWith ArqUX — what the flow seeks to structure
Instructions spread across chats and filesWorking rules locatable in the governed workspace
Agents with ambiguous context and responsibilitiesExplicit identities and contracts the agent consults
Tasks born in conversation, no shared closure criteriaWork expressed in units with scope and acceptance
State dependent on one session's historyPersisted artifacts you can inspect and resume
Review focused only on the final answerChanges and available evidence can be reviewed

The right column describes the model the flow is designed to provide — per capability, the Framework page states what is enforced by code and what is a contract read by the agent.

Follow the work

Define → Assign → Execute → Review and continue.

Each step states who participates, what goes in, which rule applies, what changes, what gets stored — and what another person can verify. Expand a step to read it. No animation required.

01 Define Team practice
Who participates
The responsible person (architect, tech lead, founder).
Input
Objective, scope, working rules, authorized knowledge, acceptance condition.
Rule applied
Policies and identity contracts agreed for the project.
What changes
The project/cycle takes explicit form: goal, constraints, closure criteria.
What is stored
Artifacts in the governed workspace (files the tooling reads).
What can be verified
That the rules and scope are written down and versioned.
02 Assign Contract in code
Who participates
The person assigning work and each agent identity involved.
Input
Task unit with scope, constraints and acceptance criteria.
Rule applied
Role and permissions of the identity that receives the work.
What changes
Work has an explicit owner; the agent has an explicit contract.
What is stored
Identity contract, assignment, and the task's recorded state.
What can be verified
Who was assigned what, under which role and limits.
03 Execute Depends on harness
Who participates
The agent — within what its harness and configured tools permit.
Input
The local directives its harness reads and the artifacts in the workspace.
Rule applied
The common policy, projected into the local files each harness consumes.
What changes
Code, files or state — per the operations actually demonstrated by the release.
What is stored
Outputs and change trail according to the version's evidence capabilities.
What can be verified
That a rule was present in the local file; whether it was enforced depends on the harness.
04 Review and continue Team practice
Who participates
A person reviewing; possibly a second agent re-delegated.
Input
Outputs, available validation results and evidence trail.
Rule applied
The acceptance condition defined in step 1.
What changes
Accept, return, re-delegate or correct — per the version's capabilities.
What is stored
The review outcome and next state of the work unit.
What can be verified
A new session can inspect the shared state and resume; synchronization follows the mechanism your team uses.
Six dimensions

What "governed" means, dimension by dimension.

The hexagonal symbol as explanatory navigation — not a security argument. Each dimension answers one question and points to a real artifact.

1 · Identity
Who is acting?
Agent identity contract.
2 · Contract
What limits and responsibility?
AXM/LIM/FCS or the current contract.
3 · Context
What knowledge and state does it receive?
brain.cortex, AGENTS.md or another context file.
4 · Decision
What must it decide, by which criterion?
Blueprint, rule or recorded decision.
5 · Execution
What task changes, and how?
Task, handler or file change.
6 · Evidence
What lets someone review what happened?
Test result, diff, event or available record.

Security and limits

Governance is only useful if you know what it enforces — and what depends on the agent.

What ArqUX does not guarantee: it does not replace human review; it does not guarantee that an agent obeys instructions in every environment; and it does not turn a hash or a log into an independent audit. Review the permissions, security and evidence model for the scope of each mechanism.

Platform · In development

The direction: a central memory service — not available yet.

The Platform investigates what a governed team needs beyond local files: one service where memory writes are validated and chained, context is served ready-made, and evidence can be exported. Hypotheses under study:

Hypothesis 1

Central, ordered writes

Whether a single authoritative journal removes the concurrency and drift problems of file-based governance.

Hypothesis 2

Evidence as an export

Whether auditors can verify integrity from hashes alone — without reading memory content.

Hypothesis 3

Permissions at scale

Which role × base × operation model teams actually need before it becomes bureaucracy.

No dashboard, no dates, no pricing until decisions and verification exist. Pilots are the way in.
