Decide with evidence

Know what ArqUX controls — and what remains under your responsibility.

Not all governance depends on the same layer. Part of it is checked in code, part requires the agent to read instructions and part belongs to your team. Here you will find the tests, the scope and the limits of ArqUX 1.0.0.

  • What the code controlsWhich rules the framework enforces in code — and which still depend on the agent or your team.
  • What is verifiedEach capability tied to a version, a source and a kind of test.
  • What to check before adoptingVersion, governance, coordination, integrity and integration — each with its check.

Explicit responsibilities

The code validates, the agent interprets and the team decides.

Telling these layers apart keeps you from asking an instruction to do what only a code control can enforce — or attributing to the framework decisions that remain human.

01

Controls that run

The framework validates inputs, roles and certain operations on the routes 1.0.0 implements and tests — for example, task.run executes only declared actions under a bound session. Which handlers apply each control is versioned and checkable.

Inspect versioned controls →
02

Instructions that guide

An agent can use AGENTS.md and its projections when its environment reads them; sync-harnesses renders four native targets from one kernel. A file's existence does not ensure the model obeys it, and copies are not synced in the background.

See integration conventions →
03

Criteria you approve

Responsible people define permissions, review results and decide which evidence they accept. The agent can propose; it cannot accept on your behalf, and ArqUX does not replace that responsibility.

Review limits before adopting →

A hash verifies consistency against a trusted reference; it does not prove identity or constitute an independent audit.

Responsible adoption

Five limits worth checking before using ArqUX.

ArqUX provides concrete controls and references, but its scope depends on the version and the environment. These are the five points worth reviewing before adopting it in your project.

Framework v1.0.0 · verified 2026-11-20

Read before adopting
1 · Version and distribution

Do not confuse the 1.0.0 source with the published package: PyPI served arqux 0.9.0 when this guide was verified (2026-11-20). Install the pinned revision and check arqux --version.

Consequence, how to check it and versioned source

Concrete consequence: pip install arqux installs 0.9.0 — a different version from the audited one; the claims on this page do not apply to it. ArqUX 1.0.0 lives in the source, at the pinned commit, until it is published to the index.

How to check it: install from the pinned source or check arqux --version; look at PyPI again before adopting.

2 · Governance: code vs. instructions

An instruction is not equivalent to a code restriction. If an action must be prevented, check that an implemented control exists on the relevant route.

Consequence, how to check it and versioned source

Concrete consequence: the code enforces only what the release implements and tests — permissions, validation and bounded execution; everything else lives in instruction files the agent may read or ignore. A rule written only in AGENTS.md or in a projection depends on the harness's obedience: it bounds intent, not capability.

How to check it: tell code-enforced controls apart from instruction-level rules; keep in handlers what must be impossible to skip.

Versioned source:

Evidence rowsHANDLERS.md ↗
3 · Coordination

The coordination available is explicit and local — a journal with push-delta/pull-policy, not a hosted service. drift-check and deliberate operations are required; hosted multi-user Platform is not part of 1.0.0.

Consequence, how to check it and versioned source

Concrete consequence: governing several teams or machines requires your own process, and drift only surfaces when you run sync-harnesses or drift-check; there is no hosted multi-tenant service in 1.0.0 — Platform is direction.

How to check it: the journal orders push and pull explicitly with optimistic locking (ERR_CONFLICT_VERSION); run drift-check after editing projections.

4 · Integrity and evidence

A hash detects changes; it does not prove who acted. Verify trusted references, export scope and privacy measures.

Consequence, how to check it and versioned source

Concrete consequence: you can detect that your artifacts changed, but there is no independent audit, signature or security certification: a hash does not prove the publisher's identity. The codec certificate covers only the codec — its scope is detailed in the evidence section.

How to check it: sealed manifests and cortex-verify detect tampering against a trusted reference (ERR_HASH_MISMATCH); evidence export blocks private fields unless a flag is explicit. Run cortex-verify on exports and review the documented threat model.

5 · Integration

Each client interprets instructions its own way. Check which file it reads, whether it allows MCP and what adhesion tests exist for your environment.

Consequence, how to check it and versioned source

Concrete consequence: harness behaviour is external — ArqUX renders four native targets (AGENTS.md, CLAUDE.md, GEMINI.md, .opencode/instructions.md) from one kernel, but how each application reads them belongs to that application; adhesion declared on nine harnesses is project-reported, with a test sheet pending. "Works with my agent" depends on your tool honouring the files and the MCP you configure; projections do not sync by themselves.

How to check it: check the compatibility matrix; re-render with sync-harnesses and check drift.
